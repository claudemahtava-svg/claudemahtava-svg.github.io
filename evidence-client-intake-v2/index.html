This page is the run record for the evidence pack named below. It lists what we tested, when, what we observed case by case, and what we did not test. It is generated from the pack file in our repository, so it cannot quietly drift from the source. Identifiers that would expose our accounts (record ids, run ids, message ids, addresses) are left out on purpose; the underlying files are available on request.

The question this pack answers

When a step in a free-tier intake automation fails, can the workflow be made to keep running, tell the operator what happened, and still acknowledge the lead?

How we tested

The scenario was edited through the automation platform's API, then exercised with scripted browser submissions against the live form. Failures were induced on purpose in a controlled window and reverted immediately afterwards. Each run was checked in the run history for status and operation count, in the CRM for the records, and in the receiving mailbox for the alert and the acknowledgement. Header authentication results were read from the delivered message.

"Confirmed" means the outcome held in every round we ran that case, which for several cases is a single round. Where a case was seen once, the status column says so, and every page that cites it says "observed once". We do not treat one observation as a pattern.

What the pack establishes

  • Handled errors do not increase the scenario error counter and do not switch the scenario off.
  • The Resume directive keeps the lead acknowledged when a later step fails, and leaves the deal unlinked.
  • The Ignore directive drops that submission cleanly; the existing record is not updated from it.
  • The alert email can carry the scenario name, the failed step, the platform error text, the run identifier, a link to that run, every form field, and the created record identifiers.
  • Directives themselves are not billed; the alert email costs one credit.
  • An authenticated sender domain removes the shared-domain rewrite seen in v1 (observed once, 2026-08-22). Our template page still describes the earlier unauthenticated behaviour; that update is queued and not yet published.

What it does not establish

  • Most cases were observed once. The association-failure case was observed twice (once in the base version and again with the enriched alert text), and the healthy path three times. Every page that cites a single observation says so.
  • The create-contact failure was induced with an invalid property, not by a real duplicate race.
  • The run link in the alert was read in the delivered message; it was not opened from a signed-in browser during the test.
  • A literal equals sign followed by two hexadecimal digits in the alert body was mangled in transport once; the final text avoids equals signs.
  • The transactional acknowledgement still carries the mail provider's open-tracking pixel and an unsubscribe header; turning that off is queued.
